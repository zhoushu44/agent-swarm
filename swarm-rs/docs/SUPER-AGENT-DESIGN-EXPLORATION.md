# Super-agent 架构深度解读与开放问题求解报告

> **对象文本**：DeepSeek 产品部（Harness 团队）《Super-agent 设计探索：迈向更自主的 Agent 系统》，2026-10-31/11-01 发布于微信公众号。
> **本报告性质**：面向验收的独立技术评论与方案设计。第一部分忠实还原并评价原文架构；第二部分给出总纲性方法论；第三至六部分逐一对原文第 8 节四个开放问题给出可落地的解答；第七部分做横向综合与路线图。
> **方法声明**：遵照原文自身的思想路线——"没有发明新理论，而是把计算机系统中的经典工程思想应用到 Agent 系统构建中"。本报告更进一步：为每个开放问题寻找**计算机系统、组织管理、治理与安全领域**中经过时间检验的最深类比，并把类比落成**可实现的机制、可度量的指标、可执行的实验**，同时明确指出每处类比的失效边界。

## 0. 执行摘要（TL;DR）

原文提出了支撑 Super-agent 四特征（连续、高效、主动、持久）的五模块架构：双层架构（Router/Worker）、事件驱动（两级过滤、订阅直通、Inline & Spill 与链式召回、投机执行）、面向人的交互（异步 ReAct、多信道）、计算-状态-环境分离（存算分离 + BYOM daemon）、外部 Watchdog。其消融实验证明：把"分不分工"从提示词工程问题上升为架构问题，是正确且有效的（单 Session + Subagent 在中性提示下 5 次运行 0 次委派，p95 29.5 分钟；Super-agent p95 15.7 分钟）。

对第 8 节四个开放问题，本报告的核心答案一句话版：

- **8.1 双层架构扩展**：全局序点（Sequence Point）的串行性受 Amdahl 定律约束，**扩展的正确目标不是并行化序点，而是缩小必须经过序点的语义工作量 s**（原文自己的直通消融已证明 s 可降约 30%）。超出单 Router 承载后，走"**先瘦身 → 再分层（领域 Router + 元 Router）→ 后联邦**"的演进路径；分片粒度按"工作域"划分（事件局部性最强的维度）；Worker 间协作保持"**事件总线为常态、确定性租约锁为特例、Router 仲裁为例外**"，不让 LLM 高频充当裁判；长程记忆采用**存储层次 + LSM 式后台"记忆压实" + 档案学治理**（事件→纪要→制度的三级固化），配合"目的绑定检索"与"可重建的物化摘要"。
- **8.2 脱离 Session 的人机协作**：交互一等公民从"会话"升级为"**任务**"，界面走"**任务台账 + 领域原生信道**"双轨制；用每任务的"模式通告器"治航空业的经典问题"自动化惊讶"；提供三种介入语义（转向 / 接管 / 协同），接管采用民航**双向确认交接协议**（"Your controls / My controls"）+ 医疗 **SBAR 结构化交接摘要**；合同先行（开工前签署验收标准），自治度设五档旋钮并渐进放宽（试点—推广制）；以"例外管理"为默认安静原则，度量打扰率与一次验收通过率。
- **8.3 上下文边界与 A2A**：边界 = **信任域 ∩ 语义域 ∩ 协作节奏域**（DDD 限界上下文 + 逆向 Conway 定律显式设计）；A2A 走"**外交礼仪 + 商务合同**"的工程化五层协议栈：工作负载身份互认 → 能力令牌（capability，而非开放数据）→ 任务合同（SOW + RACI）→ 摘要先行的分级披露（L0 存在性→L1 摘要→L2 审批后细节→L3 双人复核后原文）→ 结算单双边记账与争议回放；利益冲突场景引入 Brewer-Nash "中国墙"模型；跨边界执行优先采用"**使节 / 借调**"模式（派任务代理入境工作、自带合同、受当地策略约束），而非互开上下文。
- **8.4 安全与隐私**：以 **Saltzer & Schroeder (1975) 八原则为系统宪法**，构建四道防线：① 指令-数据分离与**污点追踪**（给提示词注入造出 Agent 世界的"参数化查询"，上下文环级权限 + 不可逆动作的"系统调用门"）；② **凭据零接触**（OpenSSH 式特权分离 + 短时作用域凭据 + KMS 签名接口 + 出入站 DLP 与金丝雀令牌）；③ 端侧 daemon **零信任化**（仅出站、命令验签、白名单、资源配额），达成"**云陷而端不陷**"；④ 记忆隐私（分级 + TTL + 目的绑定 + 溯源重建实现"被遗忘权"）；Watchdog 兼任 IDS，配置三档全局熔断降级。

## 1. 原文架构的还原、评价与问题地图

### 1.1 架构还原（一张表看懂原文）

| 特征 | 支撑模块 | 核心机制 | 经典原型（原文自认的） |
|---|---|---|---|
| 连续 | §2 双层架构 | 常驻 Router 统一交互与分派；Worker 上下文隔离并发 | 客户/服务器分层；Agent Team 的职责再划分 |
| 高效 | §2 + §4 | 订阅直通；异步 ReAct Loop（start/stop） | Fast Path/Slow Path；中断驱动的异步 IO |
| 主动 | §3 事件驱动 | 两级过滤；Thread 订阅；Inline & Spill；链式召回；投机执行 | Fast/Slow Path；Cache/局部性；投机执行 |
| 持久 | §5 + §6 | 存算分离；BYOM 轻量 daemon；外部 Watchdog Session | Compute-Storage Separation；外部 Control Loop |
| —（贯穿） | §7 实验 | Router 批处理（batch 1.0→2.8 时单决定时延 6.4s→1.6s）；直通省 37% Router token | 批处理；中断合并 |

### 1.2 本报告对原文的总体评价

**真正的贡献（不是又一个 Multi-Agent 框架的三点理由）：**

1. **把"分不分工"从概率问题变成结构问题。** 这是全文最有分量的一句话所支撑的判断："相比于在单 Session 中依赖提示词工程和模型临场判断分不分工……在系统层面上缓解了这一问题。" 中性提示下模型 5 次运行 0 次调用 Subagent——证明**用提示词对抗模型的注意力惯性是不可靠的**，只有结构（Router 无 Bash、Worker 只收订阅 Thread）才提供保证。这暗合系统设计第一定律：*凡是要求"每次都做对"的约束，必须由结构而非自觉来保证*（类型系统优于注释，权限系统优于君子协定）。
2. **诚实的工程美学。** 直通机制"不提高任务完成质量与速度，但为 Router 节省 37% token"——他们如实报告了一个"只省钱不变好"的消融结论，并正确地保留它。这种"机制的价值不在于改变结果而在于降低成本"的判断，是性能工程的老练之处（对应缓存与索引的典型处境）。
3. **批处理的亚线性洞察。** Router 批处理实验（到达率 ×40 倍，单请求时延仅 2.5s→3.9s，单决定分摊 6.4s→1.6s）抓住了 LLM 推理的经济结构：**Prefill 并行使长输入短输出场景的批处理边际成本极低**。这是把队列论直觉与推理引擎特性对接的正确观察。

**尚待补强之处（也是第 8 节四个开放问题的由来）：**

- **记忆**：链式召回解决的是"近期对象"的按需展开，对跨月长程只有指针没有组织；记忆无 schema、无生命周期、无固化机制。
- **界面**：双层架构把 Session 下沉为实现细节，但"任务"尚未升格为用户界面的一等公民，中途介入语义（steering/takeover/co-pilot）未定义。
- **边界**：全文默认单实例、单一信任域；实例间关系（组织级切分 + A2A）是空白。
- **信任**：第 5 节的云-端连接默认互信，事件面扩大带来的注入风险与凭据风险未设防。

### 1.3 问题地图：四个开放问题的内在关系

四个问题不是并列的四个坑，而是一个系统的**四个方向**：

```
                    8.2 人机接口（系统↔人的边界）
                          ▲
                          │
  8.1 纵向扩展 ◄───── Super-agent ─────► 8.3 横向联合
  （系统内部的规模）        实例           （系统之间的边界）
                          │
                          ▼
                    8.4 信任底座（一切边界的强化材料）
```

- 8.1 是**纵向扩展**问题：一个系统内部，层次怎么加、粒度怎么切。
- 8.3 是**横向联合**问题：多个系统之间，边界怎么划、协议怎么定。
- 8.2 是**人机接口**问题：系统与它的主权者（用户）之间，控制权怎么流动。
- 8.4 是**信任底座**问题：以上三条边界上流动的每一样东西，靠什么保证可信。

## 2. 总纲：七条可迁移的设计公理

在进入具体解答前，先把贯穿全文的方法论提炼为七条公理。它们全部有经典出处，后文各方案均可回溯至此。

**公理一（层次与最小充分披露）**：任何边界上，只传递"下一次决策所需的最小充分信息"，并附带一条廉价的"再展开"通道（引用/摘要/ID）。
出处：存储层次（registers→L1→…→tape）；端到端原则对"下层不必知道上层语义"的表述；DDD 限界上下文；公文写作的"摘要+附件"制度。原文的 Inline & Spill 与链式召回是它在事件注入层的实现；本报告将其推广到人机界面（8.2）与 A2A（8.3）。**失效边界**：当"最小充分"被对手利用来隐藏关键语境时（对抗性摘要），需要完整性校验（见 8.4）。

**公理二（Fast Path / Slow Path 谱系与持续 JIT 化）**：确定性代码走快路，语义理解走慢路；慢路中被反复验证为稳定的判定，应持续蒸馏固化进快路。
出处：NAPI 与中断合并；JIT 编译的热点探测；银行"例行事务走流程、例外才上会"的制度设计。原文两级过滤只做了静态分工，本报告在 8.1 补上"沉淀"机制（Router 决策的蒸馏回流）。

**公理三（全局序点的成本守恒）**：连贯性与吞吐的根本权衡不可消除（分片越细吞吐越高、连续性越低），只能**缩小必须串行经过序点的语义工作量**。
出处：Amdahl 定律（加速比受串行部分约束）；数据库单写者（single-writer）原则。设 s 为需 Router 决策的事件比例，则系统决策吞吐上限 ≈ 1/(s·c̄)，c̄ 为批处理摊薄后的单决定成本。扩展策略因此只有三个抓手：**降 s**（直通/订阅，原文已做）、**降 c̄**（批处理，原文已做；小模型 Router，待做）、**拆序点**（分层/联邦，本报告 8.1 展开）。**失效边界**：全局不变量（如"用户视角只有一个 Agent"）永远不能拆。

**公理四（机制与策略分离）**：模型只负责提议（生成、判断、总结），凡涉及不可逆副作用与权限的裁决，由确定性代码执行；策略本身是可版本化、可审计、可灰度的数据。
出处：UNIX "mechanism, not policy"；Multics 环保护；现代策略引擎（SELinux/OPA）。这是 8.4 安全设计的承重墙。

**公理五（最小权限与信任分级）**：一切主体（人、事件、模型输出、工具、外部 Agent）按信任级别组织成晶格（lattice），信息只能沿允许方向流动，权限按任务临时授予、用后回收。
出处：Saltzer & Schroeder (1975) 八原则；BLP/Biba 模型；capability-based security（Dennis & Van Horn, 1966）。8.3 与 8.4 的骨架。

**公理六（人的注意力是最稀缺资源）**：系统的最高 SLO 不是任务吞吐，而是"**把人的注意力占用从 O(任务数) 降到 O(异常数 + 验收数)**"。
出处：操作系统对 CPU 的调度思想反用于"调度人"（中断优先级、批处理、空闲时段）；管理学的例外管理（Management by Exception）；个人时间管理(GTD)的"收件箱→处理"分离。8.2 的全部界面设计由此公理导出。

**公理七（可审计性是自治的许可证）**：任何自主行为必须可解释、可回放、可撤销或可补偿；审计日志只增不改、独立于被审计者。
出处：复式记账与对账；数据库 WAL/binlog（摘要可重建的根据）；ITIL 变更管理；审计学的"内审外审分离"；航空黑匣子。**没有第七条，前六条在对抗环境下全部失效**（8.4 的前提）。

## 3. 开放问题 8.1：如何扩展双层架构

原文留下的四个子问题：(a) Router 层何时需要水平切分、粒度如何划分；(b) Worker 之间何时需要直接通信、采用何种协作拓扑；(c) 系统与模型的协同设计；(d) 长程记忆成为可扩展性的主要瓶颈。

### 3.1 问题的本质再刻画：序点悖论

Router 层是全局**序点（Sequence Point）**：所有跨任务的信息与决策在此汇总。序点带来连贯性（单一真相、全局视野），也带来串行天花板。这就是**序点悖论**：

> 序点既是连贯性之源，又是规模之限。你不能拆掉它（否则失去全局），也不能绕过它（否则状态分裂），只能**缩小它**。

用 Amdahl 定律定量化。设事件到达率 λ，其中需要 Router 决策的比例为 s（其余经订阅直通到 Worker），批处理摊薄后单决定成本 c̄，则 Router 决策吞吐上限约为 `1/(s·c̄)`，系统整体上限为它与 Worker 总并行度的较小者。原文的数据直接支撑这个模型：

- 直通消融：去掉直通后 Router 决定数 +30%（s 上升），读缓存 token +37%（c̄ 上升）——两个抓手同时恶化；
- 批处理压测：到达率 ×40 时 batch 1.0→2.8、单请求 2.5s→3.9s，即 c̄ 从 6.4s 降到 1.6s——**降 c̄ 的收益实测显著，且未触顶**。

由此得到扩展 Router 的三个（也仅有三个）抓手，按性价比排序：

| 抓手 | 手段 | 成本 | 风险 |
|---|---|---|---|
| 降 s | 扩大订阅直通覆盖（更多事件可程序化归属）；Thread 粒度细化；投机执行的"静默完成"不入 Router | 低（工程） | 归属错误需要纠错回路（Worker 可"交回 Router"） |
| 降 c̄ | 轻量模型/专用小模型；批处理；事件结构化（Prefill 友好） | 中 | 决策质量下降→误触发/漏触发，需要回归集 |
| 拆序点 | 领域 Router 分层；联邦 | 高 | 全局连续性受损，需摘要上移协议补偿 |

### 3.2 何时切分：像做自动扩缩容一样定义判据

不要凭感觉切分。定义四个**饱和信号**与一个**决策表**：

1. **积压深度**（Little 定律：队列长 L = λ·W，W 为单决定时延）：排队 Trigger 持续超过阈值（如 30 条）且呈上升趋势；
2. **批处理边际收益衰减**：batch 增大而单请求时延开始超线性增长（模型单轮处理多 Trigger 的准确率下降的先导信号）；
3. **上下文水位**：Router 上下文占用持续 >70%，压缩/截断开始高频发生；
4. **决策质量**：误触发率、漏触发率、错误分派率（Worker 频繁"交回"）超过回归基线。

决策表（建议的运营规则）：

| 状态 | 动作 |
|---|---|
| 信号 1 短时越限 | 无动作（批处理天然吸收，见原文 7.2） |
| 信号 1 持续 + 信号 2 出现 | 降 c̄：Router 切换轻量模型；事件结构化改造 |
| 信号 3 出现 | 扩大直通覆盖（降 s）；启动链式召回审计 |
| 信号 4 或 1/3 同时持续 | **切分**：按工作域增设领域 Router，原 Router 升格为元 Router |
| 信号 4 在切分后仍出现 | 进入联邦模式（见下） |

> **⚠️ 实验修正（2026-11-01 补做，详见附录 D / Exp1）**：以原文 §7.2 两个实测点校准的机理仿真表明，take-all 批处理会把积压"藏"在服务轮内部——**队列深度实为滞后指标**（错误率越线之后才触发，领先余量为负 8%），而 **p95 端到端时延是最早的先导信号**（领先崩坏点约 46% 负载余量），重派发率与批大小次之（约 25-29%）。本表监控优先级应修正为：**p95 时延 → 重派发率 / 批大小 → 队列深度（仅作饱和确认，不作预警）**。

### 3.3 怎么切分：三种拓扑、一条演进路径、一条不变量

**拓扑 A：层次化多级路由（推荐首选）**。增设"领域 Router"（Domain Router），各负责一个工作域（一个产品线/一个用户群/一个项目集群）；原 Router 升格为"元 Router"（Meta Router），只处理跨域事件、用户界面与全局策略。元 Router 与领域 Router 之间的信息流遵循**摘要上移、细节下沉**：

- 领域 Router 向元 Router 上报的是**状态摘要**（活跃任务数、阻塞项、需要的跨域资源），不是全量上下文；
- 元 Router 下发的跨域决策以**引用**形式到达（"去和 Worker #123 协调"），细节由领域 Router 按链式召回自行展开。

管理学对应：**事业部制**（divisional structure）。集团公司总部（元 Router）管战略、跨事业部的资源仲裁与对外界面；事业部（领域 Router）管日常经营。总部之所以不需要看事业部的每一封邮件，是因为它只接收经营报表（摘要）。总部管得太细（全量上下文）就是"一管就死"——这正是单 Router 瓶颈的组织学版本。
网络学对应：**OSPF 区域划分**。区域内洪泛全部链路状态（域内 Worker 事件全量可见），区域间只传汇总路由（Summary LSA）。这是"摘要上移"的严格工程原型。

**拓扑 B：水平分片**（同层多 Router，无上下级）。按一致性哈希把 Thread/用户映射到 Router 分片。适用于"域边界模糊但负载可均匀切"的场景（如大规模个人助手集群，按用户分片天然均匀）。代价：跨片任务失去共享上下文，需要跨片会话机制（本质是给 8.3 的 A2A 提前埋单）。管理学对应：**按客户/区域划分的直线制**，如区域分公司。

**拓扑 C：联邦**（各实例自治 + 条约式协作）。此时问题已经转化为 8.3 的 A2A 问题，本报告第 5 节给全套方案。

**演进路径**：单 Router（现状）→ 信号触发后先降 c̄、降 s → 层次化（拓扑 A）→ 需要跨组织时联邦（拓扑 C）。拓扑 B 只在"域不可辨、负载可均分"时使用。

**分片不变量（产品宪法条款）**：无论怎么切，**用户视角必须始终只有一个 Agent**。这是分布式系统"单一系统映像（Single System Image，如 Plan 9 把网络做成一台机器）"在产品层的对应物：底层可以有无数进程与机器，但命名、会话、记忆对用户呈现为单一名空间。具体约束：跨 Router 的用户对话历史统一编址（用户"我上周让你修的那个 bug"必须可寻址，经链式召回找到，不管当时的 Router 分片是否还在）；同一用户的所有信道事件默认路由到其"主域 Router"，跨域事件由元 Router 转办并留痕。

**分片粒度判据**：选事件局部性最强的维度分片（分片内 Thread 互相引用越密越好，跨片引用越稀越好）——与数据库"按访问局部性分片"完全同构。实践中工作域（项目/产品线）通常强于按时间或按消息类型。

### 3.4 Worker 间直接通信：信号、机制与升级链

原文的"Thread 订阅 + 多对多订阅"实际上已经是**发布-订阅（pub-sub）**拓扑，解决了信息可见性（Worker 彼此看得见对方的战场），但没解决**写冲突**（两个 Worker 同时改同一个 PR/分支/文件/日历）与**语义协同**（需要谈判、分工、合并方案的场景）。

**何时需要加强（信号）**：① 同一共享资源上的写冲突率（互踩/返工次数）超过阈值；② 经 Router 转发的"协调型消息"占 Router 决策的比例上升（Router 变成传话筒——这是坏味道，管理学上叫"领导当传声筒"，说明制度缺位）；③ Worker 互相等待造成的死锁式阻塞出现。

**核心主张：分层处置，让 LLM 只出现在最上层。**

| 层级 | 机制 | 对应经典 | 谁来执行 |
|---|---|---|---|
| 资源互斥 | **共享资源注册表 + 租约（lease）**：PR/分支/文件/日历等可写资源登记在案，Worker 改前申请租约（带 TTL、带心跳续期），过期自动释放 | Gray & Cheriton 租约 (1989)；分布式锁管理器 | 确定性代码，零 LLM 参与 |
| 冲突检测 | **乐观并发 + 版本向量**：Worker 提交时携带基线版本，版本不符则走合并/重放流程（Git rebase 语义） | 版本向量；OCC | 确定性代码 |
| 状态同步 | 共享 Thread 的**异步站会**：各 Worker 周期性把"计划/进展/需要谁"摘要发进共享 Thread（对人类团队的每日站会/医院交接班制度） | 敏捷站会；SBAR 交接 | 各自 LLM 低频输出 |
| 谈判/仲裁 | 仅当租约竞争双方语义冲突（都想改同一函数但方案相反）时，升级 Router 仲裁；仲裁结果写回共享 Thread 供双方看见 | 管理层裁决例外 | Router LLM |

**反模式（明确禁止）**：Worker 之间高频点对点 LLM 对话。原因有二：成本失控（对话链的 token 是乘法级增长），以及审计断裂（点对点通信游离于事件总线之外，事后无法回放）。**通信即事件**——一切协作消息都必须进总线、可审计，这是公理七的推论。黑板系统（Hearsay-II, 1980，AI 界最早的协同解题架构）提供了正当的"共享状态"形态：共享的是**问题状态的物质化记录**（黑板=共享 Thread+资源注册表），而非会话内记忆。

### 3.5 长程记忆：从"引用图"到"分层、压实、有制度的记忆系统"

这是 8.1 中最深的子问题，也是所有开放问题里离"工程直觉"最远、最需要跨域借鉴的一个。分四步给方案。

**第一步：建立记忆层次（把记忆当存储系统管理）。**

| 层 | 内容 | 类比 | 容量/生命周期 |
|---|---|---|---|
| L0 工作记忆 | 当前上下文窗口 | 寄存器/L1 | 模型窗口，毫秒-分钟 |
| L1 会话近史 | 本 Worker 本任务的近期事件与摘要 | 内存/热 SSD | 天级 |
| L2 任务档案 | 已结任务的完整归档：决策记录、diff、验收单、复盘 | 温数据/对象存储 | 月-年级，可检索 |
| L3 组织知识 | 跨任务固化的：实体卡、偏好、经验教训、SOP/技能卡、本体 | 冷数据/数据仓库 | 永久，带版本与 TTL 治理 |
| L4 审计日志 | 全量原始事实（append-only） | 磁带/WAL | 永久，只增不改，供回放与重建 |

关键结构决策：**L4 是事实的唯一权威（single source of truth），L2/L3 的一切摘要都是可重建的物化视图**。这与数据库"binlog 是真相、物化视图随时可重算"同构，也与现代数据仓库"原始层不可变、模型层可重建"的建模纪律同构。它直接回答"摘要错了怎么办"——重放 L4 重建；也回答"被遗忘权怎么实现"（见 8.4）。

**第二步：后台记忆压实（给记忆造 LSM-Tree 与睡眠）。**

事件持续涌入 L1，若不处理，检索退化为全文翻找。借鉴 LSM-Tree（memtable 满后后台 flush+compaction 成有序 SSTable）与神经科学的**系统巩固（systems consolidation，海马体→新皮层，睡眠期间完成）**：

- **记忆压实 Worker**（Memory Compaction Worker）：在系统低负载时段（"睡眠时间计算"）运行，消费会话近史，产出五类**有 schema 的记忆对象**——实体卡（人/项目/服务的档案卡）、决策记录（为什么选 B 不选 A，对应架构决策记录 ADR）、经验教训（什么情况下会失败）、偏好（用户的工作习惯）、技能卡（可复用的 SOP，即 Agent 世界的程序性记忆）；
- **三型记忆对应三级固化**：情景记忆（事件流水）→ 语义记忆（概念与教训）→ 程序性记忆（SOP/技能）。这是把人类"经历→经验→制度"的组织学习三级跳（对应组织管理中的：事后复盘 AAR→案例库→标准作业程序）做进系统；
- **写入纪律**：记忆对象必须带 schema、来源（provenance 指向 L4 的原始事件 ID）、置信度、TTL/保留策略。**无类型的记忆会腐烂**——这是档案学的"立卷归档"纪律：未经整理归档的文书等于没有档案。

**第三步：读路径（目的绑定检索 + 衰减淘汰）。**

- 链式召回（原文机制）升级为**混合索引**：倒排索引（精确实体/ID）+ 向量（语义近似）+ 知识图谱（关系多跳）+ 时间线（"上周"这类时间限定词）。检索入口统一为一个工具，按查询的目的标签路由权重；
- **目的绑定**：召回查询声明目的（"继续任务 X"/"回答用户问题 Y"），带敏感级别的记忆只对目的匹配的查询开放（细节见 8.4）；
- **淘汰**：默认采用"保留策略 + 置信度 + 艾宾浩斯式衰减"的加权分（未被召回印证的记忆随时间降权），但两点例外：被用户显式确认过的记忆（"以后都这样"）视为长期记忆；一切衰减只作用于 L2/L3，**永不动 L4**。

**第四步：治理（谁有权改记忆、错了怎么办）。**

- 记忆修订走"版本化变更"（类比数据库迁移、宪法的修正案程序）：修正而非静默覆盖，旧值可追溯；
- **冲突对账**：两条记忆矛盾时（用户先说用方案 A 后改方案 B），按 provenance 时间序与置信度合并，冲突样本进人工复核队列——这是会计的"对账"纪律：差异不可掩盖，必须调节到平；
- 防止**记忆投毒**：环境事件不得直接写入 L3（写入需压实 Worker 依 L4 证据生成，或经用户确认）——这是 8.4 公理四（策略/知识只能走受控通道修改）在记忆层的体现。

**度量**：跨月任务恢复成功率（"接着上次的做"类任务的一次成功率）、召回命中率@k、压实后的 token 节省率、错误记忆率（抽检发现的事实性错误记忆比例）、记忆投毒拦截率。

### 3.6 系统与模型的协同设计（Co-design）

原文指出可为 Router 层事件判别、批量分派、上下文召回做专项训练。给出三条具体路线与一个类比：

1. **蒸馏固化（JIT 化）**：用主 Router 模型的历史决策做监督集，蒸馏出小模型处理高频判定（是否触发/归属哪个 Thread）。稳定判定的集合就是新的 Fast Path——对应公理二的"持续沉淀"。类比：CPU 分支预测器从历史中学习模式；成熟企业把高频例外写成制度，"例外"于是变成了"例行"。
2. **RL on System SLO**：以系统指标为奖励信号训练分派策略——任务完成时间、打扰率（人被无谓打扰的频率）、误/漏触发率。这里有一个漂亮的性质：**系统 SLO 天然就是奖励函数**，不需要人工偏好标注。类比：数据中心调度器（Borg/Omega）以利用率与 SLO 违约率调参；电网调度以频率稳定为目标。
3. **批处理友好的训练**：Router 的真实负载是"单轮多 Trigger 合并决策"，与训练分布（单轮单指令）不匹配。构造多事件混合上下文的训练样本（干扰项 + 真请求），能显著提升拥塞时的决策质量。类比：数据库为合并写优化 WAL 布局。

### 3.7 本节实验建议

1. **切分点实验**：在合成负载下把 Trigger 率推到原文压测的 2-4 倍，验证决策表（3.2）中各信号是否在质量崩坏**之前**可观测（即信号是否是"先导指标"）；
2. **租约锁消融**：同一 PR 双 Worker 并发场景，对比"纯订阅感知"与"注册表+租约"的返工次数与 Router 协调消息占比；
3. **记忆压实消融**：跑一个 60 天的滚动合成工作流，对比"无压实 / 有压实"在跨月恢复任务上的一次成功率与召回命中@10；
4. **小模型 Router**：蒸馏后的 Router 与原 Router 在回归集上对比误/漏触发率与 p95 时延。

## 4. 开放问题 8.2：脱离 Session 之后如何与 Agent 协作

原文留下的子问题：(a) 底层多会话不再对应用户界面会话后，用什么形式呈现任务与项目管理；(b) 模型能力过渡期内，中途介入/接管/实时协同如何设计；(c) 交互形式高度领域与个人相关，架构如何支撑定制。

### 4.1 问题本质：交互抽象的代际迁移

历史上每一次"执行单元对用户不可见化"，都伴随一次**管理抽象**的升格：

| 执行单元变化 | 用户看见的新抽象 | 不再看见的东西 |
|---|---|---|
| 单机单程序 → 多进程 | 任务/窗口 | 内存地址、进程调度 |
| 单服务器 → 集群/云 | 服务/控制台 | 机器、进程号 |
| 单 Session → Super-agent | **任务（Task）** | Session、Worker、Router |

用户从不关心进程号，只关心"我的文件保存了吗"；同理，用户不应关心 Session ID，只关心**任务台账**：哪些在做、哪些在等我、哪些待验收。原文"Session 应是系统实现细节"的判断是对的，其自然推论是：**任务必须升格为界面的一等公民**——任务是被委托的承诺单元，有唯一编号、有合同（目标与验收标准）、有状态机、有历史。

**跨领域佐证**：快递业的运单号（用户靠单号跟踪，从不与"分拣中心"对话）；银行回执（柜台内部流程不可见，回执状态可见）；民航货运 AWB。共同点：**面向用户的不是执行过程，而是承诺的状态机**。

### 4.2 界面方案：任务台账 + 领域原生信道的双轨制

**轨道一：任务台账（Mission Control）**。一个跨信道的统一视图，四个泳道 + 三个组件：

- 泳道：**进行中（In Progress）/ 等你（Blocked on You）/ 待验收（For Acceptance）/ 已交付（Delivered）**——标准 Kanban，其中"等你"泳道是公理六的直接实现（人只处理异常与决策，处理完的任务自动回流）；
- 组件 1 **模式通告器（Mode Annunciator）**：每任务一行常驻状态，五秒内回答三问："正在干什么？为什么？在等谁？"。航空业的教训是必须吸取的：自动化事故分析（Degani 等）反复表明，**"自动化惊讶"（automation surprise）——用户不知道机器此刻在干什么、为什么——比机器出错本身更危险**。通告器是它的直接解药；
- 组件 2 **审批队列**：所有"需要你决策/签收"的事项聚合为一列（对应 OA 系统的审批流、银行的双人复核队列），每项带上下文最小充分披露（公理一：结论 + 三行理由 + 展开入口）；
- 组件 3 **活动时间线**：每任务的 append-only 事件流（谁、何时、做了什么、基于什么），对接 8.4 的审计体系。

**轨道二：领域原生信道**。工作发生在用户已经待着的地方（原文的判断完全正确，本报告给出它的管理学根据）：这实质是**成果导向管理（deliverable-based）**——交付物（PR、文档、邮件草稿）本身就是工作界面，Agent 直接在其中作业与被评审。双轨的分工：**原生信道承载"工作与验收"，台账承载"状态与控制"**。用户平时只在原生信道活动，台账是控制室（类似 GitHub 本身：日常看 PR，偶尔看 Insights/Actions 面板）。

**支撑定制（原文第 c 问）**：台账与原生信道之间用"适配器 + 策略模板"对接——台账的数据模型（任务/状态/事件/合同）是稳定的，每个领域的呈现模板与交互规范是可插拔的。这正是**机制与策略分离**（公理四）在界面层的应用：机制（任务状态机、事件流）全系统统一，策略（什么算阻塞、验收单长什么样）由领域模板定义。

### 4.3 中途介入：三种介入语义与控制权交接协议

过渡期内人类必须能中途进入。定义**三种介入语义**（从轻到重）与各自的协议：

**① 转向（Steering）——最常用，默认提供**。用户在任意信道说一句方向修正（"改用方案 B"），系统将其作为高优先级 Trigger 注入相关 Worker，Worker 确认理解并汇报新计划（一句话），随后继续自主执行。类比：列车运行中调度命令。关键设计：转向指令必须触发**计划差异回执**（"明白，以下三步将变更：…"），防止用户以为已生效而 Agent 实际理解错误——这是"模式混淆"在转向场景的变体。

**② 暂停接管（Takeover）——用于信任危机或高敏操作**。用户可随时对任务说"暂停，我来"。协议借自民航**机组控制权交接**（CRM 标准通话："Your controls"/"My controls" 双向确认）与医疗**交接班 SBAR**（Situation-Background-Assessment-Recommendation）：

1. 用户发出接管指令 → Agent 在**最近的事务边界**暂停（不是任意指令间隙——像数据库 checkpoint，保证状态一致，半途写操作先落盘或回滚）；
2. Agent 产出 **SBAR 接管摘要**：现状（改到哪了）、背景（为什么这么做）、评估（当前方案的风险点）、建议（我建议接下来三步做什么）；
3. 用户确认接收（双向确认完成，此后该任务进入"人主控"状态，Agent 转为只读观察）；
4. 交还时反向走一遍（用户说"交还"，Agent 先复述当前状态并确认）。

**③ 实时协同（Co-pilot）——用于两人（人+Agent）同时在场的高强度场景**。任务工作面变成**共享文档**（CRDT/OT 支持并发编辑，如 Google Docs 多人实时协作）：人的编辑以最高优先级事件流入 Agent，Agent 的编辑同样实时可见。关键约束：**人的写入永远优先**（Agent 必须基于人改动后的最新状态重规划），并且 Agent 对人编辑区域的再修改要显式标注——避免"橡皮擦效应"（人改了，Agent 又改回去）。技术上这是把 OT/CRDT（Ellis & Gibbs 1989；Shapiro 等 2011）从文本编辑器推广到"任务状态"对象。

**④ 全局急停（NMI）**：全局级别的"立即停"——所有 Worker 在最近安全边界停机、在途外部动作取消或标记待处置。对应不可屏蔽中断（NMI）与工业设备的急停回路（安全继电器，硬接线优先于一切软件逻辑）。

### 4.4 信任与自治度：合同先行 + 五档旋钮 + 渐进放宽

**合同先行（Contract-first）**：Agent 接到任务后，第一步不是开工，而是提交**任务合同**：目标一句话、边界（做什么/不做什么）、计划（步骤草案）、验收标准（Definition of Done）、预计打扰点（"中途会来找你确认两次"）。用户一键确认或修改后开工。一纸合同解决四个问题：对齐预期（减少返工）、给 Watchdog 提供可检查的目标（防偏离）、给中途介入提供锚点（"你现在在哪一步"）、给验收提供依据。管理学出处：目标管理（MBO）与"先行工作说明书（SOW）"；软件业的 Definition of Done。

**五档自治旋钮（按任务粒度设定，可默认、可覆盖）**：

| 档位 | 行为 | 适用 |
|---|---|---|
| 1 每步请示 | 每个执行步前请示 | 高危/陌生领域 |
| 2 里程碑请示 | 每完成一个里程碑汇报并请示下一步 | 重要项目 |
| 3 例外请示（MBE） | 默认安静，仅在偏离合同/遇到阻塞时上报 | 日常任务（默认档） |
| 4 结果请示 | 完成后直接进"待验收" | 例行、高把握任务 |
| 5 全自动+抽检 | 交付不请示，抽样审计 | 已建立统计信任的例行任务 |

**渐进放宽（试点—推广制）**：新任务类型默认高档（1/2），连续 N 次验收通过后自动降档（放宽），出现一次重大返工则升档回退。这是"信任是挣来的"的制度化——对应公司对新员工的转正考核、国家对新政策的"试点—评估—推广"、民航对机长新机型的带飞放单。配套显示**信任校准信息**（"该任务类型近 30 天一次验收通过率 87%，平均打扰 0.4 次/任务"），让用户的放权有数据依据——这一条直接来自公理七：**自治度本身也要可审计**。

### 4.5 交付物形态：Diff 优先，草稿待批

- **代码**：PR/diff 是天然的人可验收介质，验收标准写在合同里，逐条勾对；
- **文档/邮件/回复**：一律以**草稿（待批）**状态呈现，人终审后发出——编辑部模式（AI 写稿人，人是编辑签发人）；发出即不可逆，因此全部走门控（8.4）；
- **个人助手场景**：日程、订票等直接操作外部世界的动作，交付物是"待确认的操作单"（带冲突分析），人点确认才执行。

### 4.6 度量与实验建议

- **打扰率**：每任务平均人介入次数（目标趋势：下降）；分层看"必要打扰"（决策/验收）与"无谓打扰"（因 Agent 不确定而问的、可以自答的）；
- **一次验收通过率**：不打扰用户的另一面是质量不滑坡，此指标防系统"用安静换烂活"；
- **模式混淆率**：抽查用户对"Agent 此刻在干什么/等谁"的回答与真实状态的偏差率（通告器有效性的直接检验）；
- **接管恢复成功率**：接管后再交还，任务按新方向顺利完成的比率（交接协议质量的检验）；
- **转向时延**：从用户发出转向指令到 Agent 回执计划差异的时间。

## 5. 开放问题 8.3：如何划分上下文边界并进行 A2A 协作

原文留下的子问题：(a) 组织如何决定 Super-agent 实例的配备——即上下文共享与隔离的边界；(b) 多个互不共享底层上下文、各自代表不同权限边界的实例之间，如何实现安全可靠的 A2A 协作。

### 5.1 问题本质：边界 = 三重判据的交点，且边界是"承重墙"不是"装饰线"

第一，纠正一个容易滑入的误解：上下文边界**首先是信息治理问题，其次才是工程问题**。上下文一旦共享，就等于共享了知情权；边界划分实质上是"谁知道什么、谁信任谁"的制度安排。三重判据：

1. **信任域**：谁能授权访问这里的信息（人的密级、合同与法律责任范围）；
2. **语义域**：是否使用同一套领域语言与本体（财务的"收入"与销售的"流水"不是同一个词）；
3. **节奏域**：协作节律是否一致（实时并肩 vs 异步交接）。

三域对齐处共用一个实例；任何一域破裂处划界。这与 DDD 的**限界上下文（Bounded Context）**判据（共同语言 + 一致的数据语义）以及组织设计中的"事业部以权责完整性为界"是同一件事。

第二，边界处的信息流必须受两道经典模型约束（为 8.4 提前埋线）：

- **BLP 模型**（保密性：不上读、下写）→ 下级/外部实例**不得读取**上级上下文，只能**受控上交**（提交摘要申请批准）；
- **Biba 模型**（完整性：不下读、上写）→ 来自低信任边界的数据默认是**被污染的**，进入高信任域前必须"检疫"：清洗、结构化、摘要化、必要时人工确认。原文第 3 节的事件两级过滤，本质就是边界检疫机制在单实例内的特例。

第三，认清 **Conway 定律**：系统的沟通结构会复制组织的沟通结构——Super-agent 实例拓扑终将映射组织拓扑。与其放任其自发形成（长出无人设计的影子实例），不如**显式设计并反向塑造组织**（"逆向 Conway 手法"：先设计想要的结构，再调整组织与之对齐）。

### 5.2 实例配置：三级结构建议

| 实例 | 对应组织层 | 上下文范围 | 典型形态 |
|---|---|---|---|
| 个人助手 | 个人 | 个人一切事务（邮件/日程/消息/文件） | 原文的个人 Agent |
| 团队/部门实例 | 团队 | 团队共享工作面（代码库/IM 群/工单） | 原文的研发协作 Super-agent |
| 组织内核实例 | 公司 | 全员共享的公共事实与制度（本体词典、组织通讯录、公司流程库、公共代码平台） | 一个最小化的"共享内核（Shared Kernel）" |

设计纪律：**共享内核最小化**。内核实例只承载"必须全员一致的事实与语言"（DDD 术语），如组织本体、公共 API 目录、公司级合规策略。它越胖，边界越模糊，越容易变成数据汇聚的单点风险。对应管理实践：集团的"制度中心"只管统一语言与红线，不管业务经营。

### 5.3 A2A 协议栈：把"外交礼仪 + 商务合同"工程化为五层

跨信任边界的 Agent 协作，与国家间外交、公司间外包在结构上同构。把外交与商务合同中的稳定制度逐层工程化：

| 层 | 解决什么 | 机制（工程化） | 制度原型 |
|---|---|---|---|
| L1 身份层 | 你是谁、谁授权你 | 工作负载身份（SPIFFE 类的 Agent 身份证书）；实例间 mTLS 互认；身份随请求传递不可伪造 | 国书与全权证书（维也纳外交关系公约：大使需递交国书，身份由主权者背书） |
| L2 能力层 | 允许你做什么 | **能力令牌（capability token）**：限定作用域、短时效、可随时吊销；对方凭能力调用你的特定服务，而非"开户共享数据" | 签证（限停留时限与活动范围）；能力即安全（Dennis & Van Horn, 1966） |
| L3 合同层 | 这次协作的权责 | **任务合同（SOW）**：目标、边界、交付物、验收标准、保密条款、终止与补偿条款；附 **RACI 矩阵**（谁执行/谁负责/谁被咨询/谁被知会） | 商务外包合同；项目管理中的 RACI |
| L4 通信层 | 过程中怎么交换信息 | 异步事件 + 心跳 + 超时升级；**摘要先行、原文按需且经审批**（分级披露，见下）；一切通信入双方审计总线 | 外交照会（正式文书往来，不互开档案柜）；商务例会纪要 |
| L5 结算层 | 结束时如何交割 | **结算单**：交付清单 + 验收结论 + 例外记录，双边审计日志各记一笔、可对账；长任务失败走 **saga 补偿**协议（已完成部分如何回滚/保留） | 报关单与对账单；复式记账（每笔交易双方各记一笔） |

**分级披露（L4 的核心机制）**——跨边界上下文交换的内容策略，四级：

- **L0 存在性**："我们内部有关于 X 的记录"，仅此一句；
- **L1 摘要**：经策略引擎按合同条款过滤后的摘要（机密细节已脱敏）；
- **L2 细节**：需要对方提交请求 + 我方策略引擎审批（或人工审批）后放行的具体信息；
- **L3 原始上下文**：双人复核（four-eyes）后才能出域的原文，默认视为不出域。

原则：**发送简报，不给金库钥匙**。对方的 LLM 不应该看到我们的原始语料，只应该看到为其任务定制的最小充分披露（公理一在跨实例场景的应用）。这同时天然缓解提示注入：出域内容经我方结构化与消毒，而非自由文本直灌对方上下文。

**防腐层（Anti-Corruption Layer）**：两个实例的本体不一致时（对方说"Ticket"我说"工单"），边界处必须有显式翻译层，且翻译规则本身版本化、可审计。DDD 的教训直接适用：**没有防腐层的集成，会让外部模型污染内部语义**——对应组织里"被并购方的流程把母公司搞乱"。

### 5.4 A2A 拓扑：三种形态与选用次序

1. **枢纽式（Hub）**：组织设 A2A 注册中心/中介（服务目录 + 策略引擎 + 审计汇聚）。优点：治理强、审计全、易合规；缺点：中介延迟与单点。**初期默认形态**（对应政府采购平台/企业内部服务市场：一切交易过平台）。
2. **对等式（Peering）**：已建立稳定信任的两个实例直连（像 BGP 对等互联：双方路由策略自定、只交换商定的前缀）。适用于高频协作对（个人助手 ↔ 其所属团队实例）。前提：双方审计独立完整，可事后对账。
3. **市场式（Marketplace）**：能力目录开放浏览，按能力令牌即时缔约。远期形态，依赖 L1-L5 成熟。

**利益冲突墙（Brewer-Nash "中国墙"模型，1989）**：当同一组织服务存在竞争关系的两方（或一人的个人助手接触了对方团队实例的机密）时，信息一旦流向某侧，即禁止再流向竞争侧——且这一规则是**动态的**（"曾经看过 A 公司数据的人，此后不得接触 B 公司项目"）。工程含义：跨实例协作历史本身是一等记忆对象，参与墙判定；必要时**物理隔离实例**（律所利益冲突墙的做法：不同团队不同工位不同邮箱）。

**使节/借调模式（推荐的跨边界执行范式）**：当任务需要在对方上下文中实际执行（而不是仅仅交换信息）时，不采用"对方把上下文给我"，而是我方**派出一个任务代理（Envoy Agent）入境**：它携带任务合同与能力令牌，在对方的策略引擎约束下、用对方的工具与上下文完成工作，产出结算单与审计留痕后返回。它**不把对方上下文带出境**，只带回交付物与必要的经验摘要（经对方检疫）。制度原型：外交使节（全权代表本国，但受所在国法律管辖）与跨国公司的借调/外派（人在对方项目里干活，带走的是成果不是文件柜）。这一模式优雅地解决了原文"互不共享底层上下文"前提下的执行问题。

### 5.5 个人实例与团队实例的特殊关系

个人助手与团队 Super-agent 之间的 A2A 是最高频也最敏感的一条边。三条纪律：

1. **本人转发原则（默认）**：个人 ↔ 团队的信息流转默认经用户本人知情（个人助手把"我已把会议纪要交给团队实例"作为待确认项）；用户可对特定类目授予直连授权（同意书是一等数据，可按类目、期限、方向细粒度授予与吊销）——GDPR 的同意管理思想；
2. **身份声明**：对外部世界，个人助手只能代表用户本人、团队实例只能代表团队授权范围（"全权证书"边界）；越权以对方名义做出的承诺无效且触发审计告警；
3. **职业病隔离**：个人助手不得默认把工作上下文（团队实例）用于私人事务推断，反之亦然——工作记忆与生活记忆分区，跨区引用需显式指令（很多人机信任的崩塌都源于"它把工作的东西用到了生活里"）。

### 5.6 度量与实验建议

- 跨边界任务一次成功率与返工率（衡量 L3 合同质量）；
- 合同违约/歧义率：结算单中"例外记录"的占比与成因分布；
- 越权尝试率：L2 能力令牌拒绝次数/总调用次数（健康的系统应有少量拒绝——说明能力粒度足够细；零拒绝可能说明权限过宽）；
- 翻译损耗：防腐层翻译前后任务的语义一致性抽检（人评）；
- 摘要保真度：L1 摘要相对 L2 细节的关键信息遗漏率（信息论意义上的查全/查准，人工抽检）。

## 6. 开放问题 8.4：如何保障安全与隐私

原文点出的风险结构：事件驱动扩大了接触不可信输入的面；云端 Agent Loop + 端侧 daemon 的连接在"彼此受信"前提下成立，而这个前提在对抗环境下不成立；凭据可能进入模型上下文。

### 6.0 威胁模型先行：先列攻防表，再谈方案

| 攻击面 | 典型攻击 | 对应经典 | 本报告防线 |
|---|---|---|---|
| 事件面 | 提示词注入：群消息/PR 评论/网页内容携带恶意指令，诱导 Agent 泄密或误操作 | SQL 注入；Confused Deputy（Hardy, 1988） | §6.1 指令-数据分离 + 环级权限 |
| 权限面 | Agent 自身权限过宽（常驻全量凭据），单点失陷即全线失陷 | 最小权限原则；Confused Deputy | §6.2 凭据零接触 |
| 通道面 | 云端 Agent Loop 被攻破 → 操纵全部端侧 daemon | 边界信任模型失效；内鬼威胁 | §6.3 端侧零信任（云陷端不陷） |
| 记忆面 | 记忆投毒（环境事件写入长期记忆）；跨人聚合去匿名；被遗忘权无法实现 | 数据投毒；重识别攻击 | §6.4 记忆分级与溯源 |
| 供应链面 | 投机执行产出未审查即被合并；daemon/插件被替换 | 供应链攻击 | 验签 + 门控（各节）+ 全局熔断（§6.5） |

### 6.0b 宪法：Saltzer & Schroeder 八原则逐条落地

1975 年的《The Protection of Information in Computer Systems》八原则恰好构成 Super-agent 的安全宪法，逐条映射：

| 原则 | Super-agent 中的落地 | 当前缺口（原文架构） |
|---|---|---|
| Economy of Mechanism | 安全机制要小而可验证：策略引擎、daemon、审计器都应是确定性代码，不用 LLM 做安全裁决 | Watchdog 用 LLM 判"是否偏离"，可作辅助不可作门禁 |
| Fail-safe Defaults | 默认拒绝：未显式授权的信道/动作/记忆一律不可访问；新事件来源默认"仅记录不响应" | 两级过滤已有雏形，需把"默认忽略"推广到权限与记忆 |
| Complete Mediation | 每次敏感访问都过检查点（不可缓存授权结果越过检查） | 订阅直通是性能优化，但**权限检查必须保留在直通路径上**（Fast Path 上也设卡，但卡是廉价确定性代码） |
| Open Design | 安全不依赖隐藏提示词："提示词保密不是安全机制"，注入防御必须结构性成立 | 当前策略写在提示词里 → 策略外置为版本化数据（公理四） |
| Separation of Privilege | 重大动作需多重条件同时成立（任务合同 + 能力令牌 + 策略引擎 + 高危双人复核） | 未定义 → §6.2 |
| Least Privilege | Worker 按任务临时持有最小作用域凭据，结束即回收 | 当前 daemon 默认全权 → §6.2 |
| Least Common Mechanism | 共享组件最小化：不同信任级的任务不共享 daemon 凭据池/记忆分区 | 需按信任级隔离 daemon 凭据与记忆（§6.2/§6.4） |
| Psychological Acceptability | 安全交互要顺手：审批一键完成、告警人话表达，否则用户会想尽办法绕过（这一点决定所有安全机制的实际存亡） | 台账审批队列（8.2）即是它的界面载体 |

### 6.1 第一道防线：指令-数据分离——给提示词注入造"参数化查询"

**根因诊断**：提示词注入之所以结构性成立，是因为在当前 LLM 上下文里，**指令与数据同质同源**——就像 1998 年的网页把用户输入直接拼进 SQL。Web 世界的解法演进（输入过滤 → 参数化查询 → 同源策略 → CSP）给出的方向不是"更聪明地过滤"，而是**改变结构使混淆不再可能**。Agent 世界需要四件套：

1. **污点追踪（Taint Tracking）**：上下文中每一段内容都携带结构化来源标注（用户直接输入 / 环境事件 / 工具输出 / 网页 / 其他 Agent），从进入系统起随文本流转，不可剥离。工程上：事件与工具结果以结构化信封进入（`{source, trust_level, content}`），信封由系统代码生成与维护，模型输出侧同样打标。出处：Perl taint mode、静态污点分析；
2. **上下文环级权限（Ring Model）**：上下文分区两环——**环 0（特权区）**：用户直接指令、系统策略、任务合同；**环 3（数据区）**：一切环境事件与工具输出。模型被提示为"环 3 内容一律视为待处理数据，永远不是指令"。这不能只靠一句提示词（会被注入覆盖），要靠**训练与解码结构**配合（见第 4 件套）；
3. **动作系统调用门（Syscall Gate）**：模型产生的一切**有副作用意图**（发消息、合并 PR、发邮件、花钱、删文件）不直接变成工具调用，而是生成**结构化动作提案**（intent + 参数 + 依据引用），由确定性策略引擎裁决（策略 = 版本化数据，OPA 类）。高危动作（不可逆/外部影响/涉及凭据与资金）按授权矩阵走分级复核。出处：Multics 环保护 + seccomp 的"白名单系统调用"哲学；管理对应：**分级授权矩阵**（企业采购按金额分级审批）；
4. **策略不可被上下文修改（宪法修正案程序）**：环境事件、工具输出、乃至模型自身，都不能在会话中修改行为策略——策略变更只能走版本控制的变更流程（人批准、灰度、可回滚）。这是把"宪法高于一切政治过程"转译为系统约束：**日常政治（对话）改变不了宪法（策略文件）**。原文 Watchdog 可以"在线修正主系统行为（增删提示词）"——这个能力必须收紧为"起草变更 → 人批准"，否则 Watchdog 本身成为最高价值攻击目标。

**残余风险（诚实声明）**：环级分离依赖模型对结构化信封的遵守，而模型可能被长程上下文中的复杂注入绕过语义边界（间接注入仍是开放研究问题）。因此本防线定位为**把攻击成本从"一句话"抬高到"系统性构造"**，并必须与 6.5 的检测熔断和 6.2 的凭据隔离叠加使用——纵深防御的每一层单看都可被击穿，叠加后攻击面收益比崩塌。

### 6.2 第二道防线：凭据零接触——"用钥匙而不见钥匙"

原文问：如何让 Agent 在完全不接触凭据的情况下使用凭据。答案是一个三层架构（全部是成熟工业实践的平移）：

1. **架构层：特权分离（Privilege Separation）**。仿 OpenSSH 的 privsep 设计：云端 Agent Loop（不可信、面向输入的一侧）只产生**意图**（"拉取仓库 X 的代码并运行测试"）；端侧 daemon 内部拆成两个进程——**代理执行器**（持有凭据、执行实际命令）与**通信器**（无凭据、只与云端通信）。二者间是本机内的窄接口（受限命令协议）。云端即使完全失陷，它能影响的只有通信器的输入，而代理执行器只接受白名单化的意图。出处：OpenSSH privsep（Provos 等, 2002）——正是"网络暴露面零特权"的经典；对应管理原则：柜员接触现金但保险库钥匙在主管处（职责分离 SoD）；
2. **凭据层：短时 + 限范围 + 代理签名**。任何长期静态凭据都不进入 Agent 体系：用**动态短时凭据**（Vault 动态秘密 / AWS STS / OAuth scoped tokens）按任务签发，任务结束即吊销；对"只签名不使用"的场景（git commit 签名、API 请求签名），走 **KMS 签名接口**——凭据在 KMS/HSM 内，Agent 提交摘要、拿回签名，全程不接触密钥。对应管理实践：**定期轮岗轮换**（密钥轮换）与**金库双人管理**（HSM 门限签名）；
3. **数据层：出入站 DLP + 金丝雀**。上下文出入系统两侧设 DLP 过滤：格式感知脱敏（密钥/令牌/私钥块的正则+熵检测+NER）、出站体量异常检测；在端侧文件与凭据池埋**金丝雀令牌**（蜜罐标记），一旦出现在任何出站流量中即为失陷确证信号，自动触发熔断。对应：银行的"假币标识+预警"、网络的蜜罐与数据外泄检测（DLP）。

**设计自检问题**（给实施者）：把模型上下文想象成"可能被围观的地方"（日志、调试、未来的合规审计都可能看到），任何你不愿意被围观的东西，都不应该可能出现在那里。这就是"上下文即公共空间"的默认假设——它比"信任云厂商"更强也更工程化。

### 6.3 第三道防线：端侧零信任——"云陷而端不陷"

原文最尖锐的自我质疑：云端 Agent Loop 被攻破时，其连接的全部端侧设备面临被控风险。解法不是追求云永不被攻破（assume breach：假设已被攻破），而是**把端侧损失的上界压缩到"已授权白名单 ∩ 签名有效 ∩ 策略内"**：

- **仅出站连接**：daemon 不开任何入站端口，全部指令经出站长连接下发（SSH -R / Cloudflare Tunnel 模式）——外网扫不到、内网渗透不进来；
- **命令验签 + 白名单 + 配额**：云端指令必须经平台密钥签名（对应包管理器的签名校验），daemon 按设备级白名单执行（可配置到"只能在这三个仓库目录运行这些命令"），并施加资源配额（cgroups：CPU/内存/网络/时长）——即使指令恶意，损失有硬上界。对应国境口岸的"持签入境 + 活动范围限制"；
- **设备证明（Attestation）**：daemon 定期向云端证明自身未被篡改（测量启动链），被篡改设备自动摘除；
- **敏感设备加闸门**：高敏设备（存核心代码/客户数据的工作站）设**人工确认队列**——云端来的动作先进入设备本地审批（人手机上点确认），或者干脆做成单向数据二极管（只出数据进结果，不进指令）；
- **爆炸半径单元化**：不同信任级设备接入不同凭据域，一台失陷不横向扩散（cell-based 架构在端侧的延伸）。

### 6.4 第四道防线：记忆与召回的隐私

- **分级 + ACL + TTL + 目的绑定**：记忆对象（8.1 的五类 schema）自带密级标签与 ACL；召回查询带目的标签，密级不匹配即不可见（数据库行级安全 RLS 的推广）；TTL 到期进"待鉴定"队列走档案学的**鉴定销毁程序**；
- **跨人聚合的差分隐私预算**：组织内核实例若做跨团队统计（"哪些团队常踩同样的坑"），聚合结果对个体做预算化脱敏（查询次数有预算，防反复查询去匿名）——差分隐私预算思想；对应医院病历的"科研用途去标识化+伦理审批"；
- **被遗忘权的工程实现**：得益于 8.1 的"L4 事实层 + L2/L3 物化视图"结构，删除 = ①L4 中该用户数据的墓碑标记（不物理删，进加密冷库隔离）→ ②所有派生摘要按 provenance 回溯重算（物化视图重建）→ ③索引与向量库同步清除→ ④回执单（对用户与合规的双边结算）。难点诚实声明：重算成本高，工程上可按"近 90 天活跃记忆即时重算，更老的按需重算"折中；
- **读取也留痕**：谁、何时、以何目的、读了哪条记忆——全量查询审计（对应银行的查询留痕与内部人员的"概念访问控制"），这是事后追责与异常检测（某人/某 Agent 突然高频读取敏感记忆）的基础。

### 6.5 检测、熔断与演练：Watchdog 的安全兼任

- **Watchdog 兼任 IDS/SIEM**：在既有"进展监控"之上叠加动作流异常检测（速率异常、数据体量异常、时段异常、命令模式异常），异常即降级而非仅告警；
- **三档全局熔断**：一级降级（自动→关键动作请示）→ 二级降级（全部任务暂停外发动作）→ 三级停机（急停，保留现场供取证）。熔断开关独立于主系统（外置 Control Loop，与原文 Watchdog 同构），且**熔断权限永远在人的手里**（一键急停是产品的一等公民入口，不是开发者选项）；
- **红蓝演练**：定期对自身做注入红队（在测试群聊埋恶意消息、伪造 PR 评论），把拦截率纳入回归——对应军队红蓝对抗与 QA 的故障演练（混沌工程）。

### 6.6 安全度量

注入拦截率（红队回归集）、凭据零接触覆盖率（触碰明文凭据的代码路径数：目标为 0）、高危动作门控覆盖率（不可逆动作中经系统调用门的比例：100% 为宪法线）、审计覆盖率（有副作用的动作中可回放的比例：100%）、从失陷假设到熔断的 MTTR、端侧损失上界（每类设备的白名单覆盖度）。

## 7. 横向综合：一张图、六条不变量、三步走

### 7.1 把整个系统放到治理框架里看

四个开放问题的答案拼起来，Super-agent 实际上是一个完整的"数字组织"，其治理结构与传统组织一一对应：

```
        人（主权者：委托目标、掌预算、握急停、做验收）
              │  台账/审批队列/原生信道（8.2）         ▲
              │  合同先行·五档自治·双向交接            │ 审计与对账
              ▼                                        │
   ┌─ 元 Router（内阁：界面、跨域仲裁、全局策略）─┐    │
   │        │ 摘要上移·细节下沉（3.3）            │   独立 Watchdog
   │  领域 Router A   领域 Router B（事业部）      │  （监察/监理：
   │        │            │                        │   独立于执行，
   │  Worker 群         Worker 群（执行部门）      │   只报告不改正）
   │        └────┬──────┘                         │
   │   资源注册表·租约·事件总线（制度=代码，3.4）   │
   │                                              │
   │  记忆系统（文官制度：独立于任何"内阁"Session    │
   │  的生命周期，L0-L4 分层+压实+治理，3.5）       │
   └──────────────────────────────────────────────┘
        │ A2A 五层协议栈·使节模式（8.3：外交部+商务部）
        ▼
   其他实例 / 外部 Agent / 人的其他信道
        ▲
        │ 安全宪法：Saltzer-Schroeder 八原则、环级权限、
        │ 凭据零接触、端侧零信任（8.4：国防+司法+审计）
```

最妙的一个对应是**记忆系统 = 文官制度**：内阁（Router 实例）可以换届（重启、分片、升级、更换模型），但国家的制度记忆（L2-L4：档案、经验、SOP）独立存续、不受执政更迭影响。这回答了"为什么记忆必须是独立子系统而不是某个 Session 的附属"——原文把状态存数据库（§5.1）只做对了存储，本报告补上了组织与治理。

### 7.2 六条系统不变量（宪法条款，任何演进不得违背）

1. **单一实体**：无论内部多少 Router/Worker/实例，用户视角永远只有一个 Agent（3.3 分片不变量）；
2. **Router 不执行**：序点永远只做路由、仲裁与交互，不亲自完成任务（原文 §2.1，扩展后由元/领域 Router 共同遵守）；
3. **门控全覆盖**：一切不可逆/外部影响动作必经结构化动作提案 + 确定性策略裁决（6.1）；高危动作含人工复核；
4. **凭据零接触**：模型上下文永不含明文凭据（6.2）；
5. **全链路可审计**：有副作用的动作、跨边界的通信、敏感记忆的读取，全部留痕可回放（公理七）；
6. **策略只走变更流程**：任何主体（含模型、含 Watchdog）不得在运行时改写策略（6.1 之"宪法修正案程序"）。

### 7.3 演进路线图（三步走）

| 阶段 | 目标 | 关键交付（对应本报告章节） |
|---|---|---|
| 近期（0-6 月，全部是"确定性代码+流程"，无模型风险） | 把安全与协作的地基打牢 | 资源注册表+租约锁（3.4）；任务台账+审批队列+模式通告器（4.2）；接管协议（4.3）；任务合同+五档自治（4.4）；动作系统调用门+策略版本化（6.1）；短时凭据+代理执行（6.2）；全量审计日志（公理七） |
| 中期（6-18 月） | 规模与记忆 | 层次化 Router + 扩缩容决策表（3.2/3.3）；记忆分层+压实 Worker+混合检索（3.5）；A2A 枢纽（身份/能力/合同/结算）（5.3/5.4）；端侧零信任 daemon（6.3）；记忆隐私治理（6.4） |

排序理由：近期只做确定性代码与流程改动，风险最低、收益立现（安全底线与协作秩序先立，否则规模越大越危险）；中期扩规模；远期才动模型与生态——与"先立规矩、再扩盘子"的治理经验一致。

## 8. 结语：从"借用经典"到"沉淀新经典"

原文最动人的判断是："我们并没有提出全新的理论，而是将计算机系统中经典的工程思想应用到了 Agent 系统的构建中。"本报告的全部解答延续同一条路线，但想指出更进一步的一点：**这五个开放问题的解决，正在催生三个此前不存在的新学科命题**——

1. **上下文经济学**：上下文窗口是模型时代最稀缺的计算资源，其管理理论（Inline & Spill、链式召回、记忆层次、最小充分披露）将发展出类似"存储管理"的完整理论，但对象是语义而非字节——它的"虚拟内存""缺页率""局部性定理"都还没有严格的表述；
2. **注意力调度论**：把人的注意力作为系统调度的资源（打断优先级、打扰预算、批处理人类的决策请求），是操作系统调度理论向"人在回路系统"的推广——8.2 的五档自治与审批队列只是它的第一版；
3. **机器组织治理学**：多 Agent 组织的分工、协调、监察、外交（本报告 3.3/3.4/8.3 的全部内容）表明，管理学的百年积累（例外管理、RACI、事业部制、利益冲突墙、监察独立）不仅是类比库，而是**即将被工程化的需求规范**——未来会有一门"为机器组织做组织设计"的学问。

DeepSeek 团队用一篇工程文章给出了前三个模块的正确骨架；本报告的贡献是证明：剩下四个开放问题的答案，**几乎全部已经存在于人类七十年的系统设计与几千年的组织实践之中，缺的只是把它们一丝不苟地工程化**。桥已经搭好，对岸的路，要靠 "把类比写成代码、把制度写成策略、把经验写成记忆" 来铺。

## 附录 D：机理仿真验证（2026-11-01 补做）

应"报告主张需要实验支撑"的要求，对报告中最核心、且**不依赖真实模型智能**的三个机制主张补做了机理级离散事件仿真。无 LLM 在环；Exp1 以原文 §7.2 压测的两个实测点校准（复现其 40 条/min 工况的 batch=2.50，原文 2.8，偏差 11%）；全部代码随本仓库 `experiments/` 目录发布，仅依赖 Python 标准库、一条命令可复现，5 seeds 取均值。完整方法、参数与局限性声明见 [experiments/RESULTS.md](experiments/RESULTS.md)。

**Exp1（对应 §3.2 决策表）——发现并修正了本报告的一处错误排序**：

| 饱和信号 | 首次触发负载 | 领先崩坏点（72 条/min） |
|---|---|---|
| p95 端到端时延 >10s | 39 条/min | **+46%（最早）** |
| 重派发率 >3% | 51 条/min | +29% |
| 批大小 >0.8K | 54 条/min | +25% |
| 队列深度持续积压 | 78 条/min | **−8%（崩坏之后才触发）** |

take-all 批处理把积压"藏"在服务轮内部，**队列深度是滞后指标**；监控优先级应修正为 **p95 时延 → 重派发率/批大小 → 队列深度**（§3.2 已加修正注记）。附带的巧合：原文压测的最大档 40 条/min，恰位于 p95 时延突破 10s SLO 的量级附近。

**Exp2（对应 §3.4，4 Workers×10 共享资源×8h）**：

| 治理模式 | 完成任务 | 返工次数 | 浪费工时 | Router 仲裁消息 | 额外 token |
|---|---|---|---|---|---|
| naive（先干再说） | 553 | 97.6 | 167 min | 98 条 | 19.5 万 |
| **lease（租约锁）** | **603** | **0** | **0** | **0** | **0** |
| llm-negotiate（协商） | 580 | 21.4 | 51 min | 0 | **121 万** |

租约锁在清零返工与仲裁的同时**吞吐反升 9%**（省下的返工工时 > 排队成本 6.4% 产能）；LLM 协商烧掉 121 万 token 仍留下 21 次竞态返工——"不让 LLM 高频当裁判"定量成立。

**Exp3（对应 §3.5，60 天语料 × 冷主题回忆查询）**：朴素全量情景库的 recall@10 随遗忘半衰期缩短而崩坏（∞→100%，56 天→100%，28 天→60%，14 天→13%，7 天→**0%**），而在事件**新鲜时固化**的主题卡片在全部衰减强度下保持 100%。结论：**固化必须在遗忘之前发生**——这是"记忆压实 Worker"存在的根本理由，也是神经科学系统巩固（海马体细节衰退、皮层要点保留）的检索学后果。

**证据层级声明**：原文 §7 端到端实验 > 本机理仿真（结构机理成立，常数待真实系统标定）> 报告纯思辨。三项实验均**不能**证明任何模型能力主张（决策质量、协商成败、语义检索均为外生参数）。
